# Engine techniques and evidence

Research snapshot: 2026-10-11. This is design research for a managed .NET 10 library, not an implementation report. Rust regex/regex-automata is the main reference; Intel Hyperscan is a secondary reference. A technique becomes a default only after semantic equivalence tests and representative measurements. No source establishes a universally fastest regex engine.

## Optional expression compiler

GregsEx uses FastExpressionCompiler.Internal.src as the runtime compiler implementation. The inspected package embeds internal C# Compile assets without a DLL; private package metadata keeps it from becoming a consumer dependency. FEC compiles expressions via DynamicMethod, and its API permits disabling fallback to Expression.Compile. GregsEx uses bounded programmatic expression construction and direct char/byte span delegates, retaining the same validated regex plan and semantics. Unsupported FEC trees are handled by the explicit/Auto policy, never by an invisible second compiler. See [the compilation specification](../specs/compilation.md).

The package's compiler class declares RequiresUnreferencedCode. Dynamic-code guards do not prove trimmed JIT safety, so source/metadata inspection and published-consumer tests are required. Source-package warning suppression is not compatibility evidence. The ordinary AOT executor must not retain or initialize this machinery.

Upstream benchmarks primarily compare against Expression.Compile, and execution improvements vary by expression and runtime. They do not prove an advantage over specialized hand-written IL or establish GregsEx results. Measure tree creation, delegate compilation, first invocation, warm matching, allocations and retained memory separately. LightExpression may reduce construction overhead but is a later candidate; select it only with equivalent semantics and measured value. Both source variants still require dynamic-code isolation.

## Meta-engine composition

The Rust source stores a common NFA alongside PikeVM, bounded backtracker, one-pass, hybrid and full-DFA wrappers. It extracts prefixes and can select literal-only execution, while DFA searches have retry/failure handling. GregsEx should study that separation of reusable representation, immutable plan and mutable workspace. It should not copy Rust's UTF-8 assumptions or Perl-like ordering into every flavor. [Verified source](https://github.com/rust-lang/regex/blob/64ad0b618e043b791ed5385dd5504a436da1ddae/regex-automata/src/meta/strategy.rs).

Proposed dispatch is capability driven before it is cost driven:

1. Normalize the flavor's semantics into IR: character domain, case policy, assertions, match selection, capture behavior and nonregular operations.
2. Use a direct literal matcher only when it can produce the exact requested result. Otherwise attach a proven necessary prefix, suffix or inner-literal prefilter to an engine.
3. For anchored regular captures, try one-pass when analysis proves a unique consuming path with compatible assertion and tag behavior.
4. For regular boolean or range search, consider a lazy DFA. Recover the start with a compatible reverse automaton when required, then recover captures through a suitable anchored engine.
5. For small regular programs and input windows, consider a visited-state bounded backtracker; otherwise use the semantic reference NFA executor.
6. Use a separately bounded VM for enabled backreferences, recursion or other features requiring history beyond the regular executor. POSIX selects its tag-aware executor before any leftmost-first engine.

This is a candidate policy, not a fixed ranking. Compilation cost, input length, captures requested, memory budgets and observed prefilter selectivity are benchmark dimensions. A prefilter must never discard a valid match. An inner literal needs a sound candidate-window derivation; its position is not necessarily the match start. If such a proof is unavailable, disable the optimization. Retain literal alternative priority and capture results, including empty alternatives.

Gallant describes reusable internals and differential tests across execution strategies. He also explains why literal candidate density can erase acceleration benefits and why an overall match can precede anchored capture extraction. GregsEx adopts composition and testing as design principles; its thresholds remain experiments. [Author's account](https://burntsushi.net/regex-internals/).

## Regular execution candidates

| Candidate | Potential benefit | Eligibility and correctness fallback |
| --- | --- | --- |
| PikeVM / Thompson simulation | Predictable regular search; captures without recursive call stack | Keep active states in priority order for leftmost-first semantics. State deduplication must preserve the winning capture state. POSIX requires a different dominance rule. |
| One-pass | Single capture register set and deterministic consuming transitions | Analyze after Unicode/case expansion. Conflicting paths, assertion ambiguity, unsupported capture semantics or build budget failure return to the reference executor. |
| Visited-state bounded backtracker | Depth-first locality on short inputs | Admission uses checked state-count × window-size arithmetic. A state/position bitmap is valid only for the regular semantics it was proved against; exceeding scratch capacity falls back before running. |
| Lazy DFA | Amortize determinization across repeated searches | Fixed-capacity per-workspace transition cache; quit/restart policy for churn, unsupported boundary context or cache pressure. Never report an interrupted search as no-match. |
| Full table DFA | Compact predictable dispatch for favorable small alphabets | Optional bounded build because state explosion is possible. Build rejection leaves the reference plan usable. |

Rust's [PikeVM](https://docs.rs/regex-automata/latest/regex_automata/nfa/thompson/pikevm/struct.PikeVM.html) supplies captures with an O(mn) regular search bound. Its [one-pass engine](https://docs.rs/regex-automata/latest/regex_automata/dfa/onepass/struct.DFA.html) is restricted to anchored execution and a subset of patterns. The [bounded backtracker](https://docs.rs/regex-automata/latest/regex_automata/nfa/thompson/backtrack/struct.BoundedBacktracker.html) avoids repeated regular-state work but has a visited-capacity/input-length restriction. These are precedents; GregsEx must prove its own complexity and semantics.

Rust's [hybrid regex](https://docs.rs/regex-automata/latest/regex_automata/hybrid/regex/struct.Regex.html) pairs forward end search with reverse start search and does not itself recover captures. GregsEx must replay capture extraction with the original input context: a bounded search region must not turn its edges into artificial `^`, `$` or word boundaries. The selected start/end and capture ordering must agree with a single reference execution. A reverse engine is unnecessary when an anchored start is already known.

The [hybrid configuration](https://docs.rs/regex-automata/latest/regex_automata/hybrid/dfa/struct.Config.html) documents cache capacity, cache-clear and efficiency controls, byte-equivalence classes and ASCII-only heuristic handling of Unicode word boundaries. GregsEx proposes bounded cache resets, an attempt limit and a reference fallback using the same remaining operation budget. A fallback restarts from the original search bounds unless a safe checkpoint is proved. Keep all attempts inside the budget so an optimization cannot hide excessive work.

## Character classes and Unicode

Candidate representations include ASCII bitmaps, sorted scalar intervals, deduplicated Unicode pages, and equivalence-class IDs. A class partition groups values indistinguishable to all predicates in a compiled program, reducing table columns. For UTF-16, classification must distinguish code units from decoded scalar values according to the chosen flavor and flags. An isolated surrogate, a paired surrogate and a supplementary scalar cannot be conflated. A byte-class approach is relevant to an explicit byte/UTF-8 representation; it does not authorize transcoding or changing reported offsets.

Benchmark direct interval membership against page tables and equivalence classes; table size, indirection, branch behavior and startup can reverse the winner. Pin Unicode data versions in generated artifacts and never substitute ASCII uppercasing, ordinal string comparison or runtime culture for a flavor's canonicalization. Keep assertion context in the partition where required. Unicode/case expansion must have compilation limits because a short pattern may produce a large automaton.

## POSIX tags and nonregular execution

An NFA recognizes a language; capture disambiguation requires additional policy. Ordinary first-thread-wins deduplication is insufficient for POSIX subexpressions even if the overall range is leftmost-longest. The reference POSIX executor needs tag histories, explicit precedence and a proven comparison when paths meet. TDFA/tag-register compression can follow after that oracle is stable. The [Trofimovich paper](https://arxiv.org/abs/1907.08837) treats tags and greedy/POSIX disambiguation separately, including repeated submatches; it supports investigating tagged automata, not assuming ordinary DFA captures suffice.

A history-sensitive VM cannot reuse a regular `(instruction, position)` visited bitmap for arbitrary backreferences or recursive calls: different captures or return stacks can change the future. Use explicit frames, capture undo records, bounded depth/memory/steps and periodic cancellation/deadline checks. Resource exhaustion is an explicit status/error. It must not silently become no-match or switch to a regular approximation. PCRE2's [documented match/depth/heap controls](https://www.pcre.org/current/doc/html/pcre2api.html) motivate separate limits; GregsEx defines its own whole-operation accounting.

## .NET search and static-data candidates

[SearchValues.Create](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.searchvalues.create?view=net-10.0) supports byte and char sets and string sets with `Ordinal` or `OrdinalIgnoreCase`; [SearchValues<T>](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.searchvalues-1?view=net-10.0) is intended for repeated searches. Prepare instances during compilation/static initialization, then test `IndexOfAny` and related span APIs as prefix/class scanners. Their comparison semantics must match the flavor or act as a sound, possibly broader prefilter. Creation is outside the warmed search allocation contract. Compare small-set scalar/bitmap paths with reused SearchValues, including short haystacks and dense candidates.

The requested [Andrew Lock article](https://andrewlock.net/removingbyte-array-allocations-in-dotnet-framework-using-readonlyspan-t/) shows a getter returning constant array data as `ReadOnlySpan<T>` can reference an assembly data blob. On older targets, the direct optimization covers byte/sbyte/bool; wider primitives such as int use cached arrays. .NET 7+ adds `RuntimeHelpers.CreateSpan` support for wider data/endian handling. Constants are required: `static readonly` values are not constants. Returning mutable `Span<T>` or a nonconstant `new T[]` getter can allocate on every access. Static-property collection expressions catch the mutable/nonconstant escape errors; locals have different lowering and no equivalent guardrail. UTF-8 literals are another static byte-span form. For .NET 10, consider constant readonly span properties for immutable tables, inspect emitted IL/AOT output and separately measure startup and steady-state. The article does not establish that each getter access is faster than a static array field. `ReadOnlySpan` is a view, not a blanket allocation guarantee.

The [AsciiHash note](https://github.com/StackExchange/StackExchange.Redis/blob/31fadaf4773d7817cb34caf8999104febb40fcfb/eng/StackExchange.Redis.Build/AsciiHash.md) describes fixed short token recognition using length/hash dispatch and sequence verification. Every hash hit must verify full token equality under the same case policy; collisions are not matches. GregsEx can benchmark handwritten/data-driven versions for parser vocabularies such as flags, property aliases or option names. Compare switches, span equality, frozen dictionaries and length/hash dispatch, including invalid/colliding tokens. Restrict ASCII folding to an ASCII-defined vocabulary. It is not regex Unicode case folding. The reference uses source generation, but GregsEx requires no source generator: it can store reviewed constants/tables and verify their derivation in tooling. Constructors and setup costs also need separate measurement.

## Secondary Hyperscan ideas

Hyperscan's [compilation API](https://intel.github.io/hyperscan/dev-reference/compilation.html) compiles pattern databases for block, streaming or vectored execution and supports multiple expressions. It rejects captures/backreferences and recursion, reports endpoints by default, and has different multiple-match ordering from PCRE. Its prefilter mode returns a superset that needs exact confirmation; databases can target CPU instruction sets. Its [runtime API](https://intel.github.io/hyperscan/dev-reference/api_files.html) separates prepared scratch from scans and requires distinct scratch for concurrent callers. These motivate research into multi-literal decomposition, shared prefix graphs, vectorized scans and explicit workspace ownership. They do not establish full PCRE2, POSIX captures or XML semantics, nor make streaming a current requirement. A managed .NET implementation must retain a scalar/table path for NativeAOT and unsupported hardware. Evaluate ISA-specific acceleration only against that path, recording hardware, database size, compile cost, scratch cost, pattern count and identical output semantics.

## Literal scans and execution inner loops

Additional primary-source snapshot, accessed 2026-10-11: [memchr documentation](https://docs.rs/memchr/latest/memchr/) identifies 2.8.3 and [aho-corasick documentation](https://docs.rs/aho-corasick/latest/aho_corasick/) identifies 1.1.5. The source revisions below were inspected directly; branch snapshots are not asserted to match those package releases. These techniques are candidate experiments, not requirements to reproduce complete upstream implementations.

**Single-literal scans.** memchr provides forward/reverse byte scans with runtime-selected vector acceleration. Its [packed-pair implementation](https://github.com/BurntSushi/memchr/blob/bd6068c30e9074a90c285e47912fa0b047d07597/src/arch/generic/packedpair.rs) compares two selected needle positions across vector lanes, combines candidate masks and verifies the full needle. The [pair selector](https://github.com/BurntSushi/memchr/blob/bd6068c30e9074a90c285e47912fa0b047d07597/src/arch/all/packedpair/mod.rs) uses background frequency ranks rather than always choosing the first/last byte. GregsEx can compare existing span/IndexOf/SearchValues operations with a prepared char-pair filter, reserving byte scans for a byte-domain backend. Preserve earliest candidate order, handle vector tails safely and never read outside the span. Measure needle length, candidate density, short-input dispatch cost and ISA availability; full equality or regex confirmation remains mandatory.

**Adaptivity.** The inspected [memmem searcher](https://github.com/BurntSushi/memchr/blob/bd6068c30e9074a90c285e47912fa0b047d07597/src/memmem/searcher.rs) combines substring strategies including Two-Way and a prefilter that can disable itself when ineffective. GregsEx should test bounded per-workspace counters for bytes skipped versus candidates verified, then bypass a dense filter without skipping unchecked input. Compare fixed rare-position ranks with corpus-specific ranks; neither guarantees rarity in the current input. Reset/retain policy must be explicit, allocation-free and safe across workspace reuse. Test repetitive adversarial text and a change from sparse to dense candidates, not just random data.

**Multiple literals.** Aho-Corasick shares literal prefixes in an automaton; its documented match policies distinguish ordinary earliest-end reporting from leftmost-first/longest. That distinction matters for `Samwise|Sam`, and overall longest selection still does not supply POSIX submatch tags. The inspected [Teddy source](https://github.com/BurntSushi/aho-corasick/blob/6c0abf5681bfc30bb9d8f7f52b68a350b436fffa/src/packed/teddy/generic.rs) uses low/high nibble shuffle masks to identify candidate pattern buckets across lanes, aligns masks across selected positions, then verifies bucket literals. Its [builder](https://github.com/BurntSushi/aho-corasick/blob/6c0abf5681bfc30bb9d8f7f52b68a350b436fffa/src/packed/teddy/builder.rs) considers pattern count and available vector features. Compare scalar literal tries, Aho-Corasick, reused multi-string SearchValues and Teddy-like filtering by literal count/length, prefix sharing, bucket collisions and match density. Preserve alternative priority and capture behavior; retain a portable exact path when the filter is ineligible.

**State storage and Unicode expansion.** Rust's inspected [sparse-set source](https://github.com/rust-lang/regex/blob/72d650cb0a880a01ab6dc2137c0888e8f89740f7/regex-automata/src/util/sparse_set.rs) stores insertion-ordered dense IDs plus sparse index lookup; membership checks the index against active length and the dense ID, while clearing resets length. This avoids clearing the entire state universe each step. Compare that structure with generation-stamped visited arrays and dense bitsets at different active-state densities. Bitset iteration order cannot replace thread/capture priority; POSIX tag dominance remains separate. Rust's inspected [UTF-8 range expansion](https://github.com/rust-lang/regex/blob/72d650cb0a880a01ab6dc2137c0888e8f89740f7/regex-syntax/src/utf8.rs) converts scalar intervals into sequences of byte intervals, embedding decoding into an automaton. Study shared-prefix/suffix compression and equivalence-class table columns to control expansion. For GregsEx UTF-16, compare scalar classification and surrogate-aware transitions directly; do not transcode input or reinterpret offsets to imitate the byte engine.

**Decomposition and bit-parallel execution.** The primary [NSDI 2019 Hyperscan paper](https://www.usenix.org/system/files/nsdi19-wang-xiang.pdf), sections 3–5, decomposes NFA graphs into required strings and smaller automata, coordinating component execution so recognized literals need not be matched twice. It also describes SIMD bucketed Shift-Or string filtering and state-bitmaps with SIMD successor calculations. Investigate small capture-free regular components first, with exact context/order verification and a scalar/table alternative. Component boundaries cannot erase assertion, greediness or capture dependencies. Bit-parallel recognition does not automatically implement PikeVM capture registers or POSIX tags. Record bitmap width, transition density, component/cache size and reconstruction cost; the paper's network-security measurements are not a GregsEx speed prediction.
